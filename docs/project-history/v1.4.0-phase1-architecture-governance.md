# v1.4.0 Phase 1 — architecture and governance design record

Date: 2026-10-25. Branch: `develop/v1.4.0` (created from the last local commit of `release/v1.3.1`). Baseline: the v1.3.0 enterprise re-audit and the Phase 0 remediation report. Scope: the architectural and governance findings that Phase 0 deliberately left open; no publication.

## 1. Router reachability (audit V13-101)

**Problem.** 19 controls were loaded by no capability and no routing rule, so no task could ever receive them. Adding them to capabilities alone would have widened the floor for every task, contradicting selective loading.

**Decision.** A canonical applicability matrix (`spec/applicability-matrix.yaml`) records, for every control, the capabilities that make it applicable (plus `always` for the minimum controls). Where a control is a genuine project-level concern (release, operations, exceptions, governance changes) a new capability and intent carry it. `scripts/validate-applicability.py` enforces the invariant statically: every non-deprecated control is reachable for the high-assurance profile from at least one intent; the capability floor is never hidden; no trigger names an unselectable capability.

## 2. Profiles that affect selection (audit V13-102)

**Problem.** Profiles only produced a blocker when below the risk recommendation; the selected set was identical across profiles.

**Decision.** An additive profile layer in `runtime/router.py`: a control required by the confirmed profile joins the route when one of its matrix triggers is among the selected capabilities (or `always`). Properties, tested in `tests/scenarios/test_profile_layer.py`: baseline ⊆ production ⊆ high-assurance for the same task; the capability floor is unchanged by the profile; every profile-layer addition is profile-required and has a trigger hit; a UI-only task never receives identity, database, API, file, secret or data controls. The existing blocker is kept.

## 3. Acceptance tests (audit V13-103)

**Problem.** Controls carried verification prose with no verifiable criterion, evidence type or automation hook.

**Decision.** `spec/acceptance/<domain>.yaml` per domain, at least two tests per control with a specific criterion, a method, a negative-path flag, allowed evidence types and an automation hook; `scripts/validate-acceptance.py` enforces completeness, specificity and uniqueness; `vcgf.py acceptance <control-id>` exposes them; `ui-select` binds the UX tests to the standards it loads. The tests describe what a target project must demonstrate; they do not execute here and never infer conformance.

## 4. Smart UI operational integration (audit V13-004/005/009/011)

**Problem.** The frozen Smart UI package was reachable only as two documents in the pack map; its 98 standards had no binding to controls, profiles or tests, and loading them wholesale would have cost hundreds of kilobytes per task.

**Decision.** Four normative user-experience controls give the package a governance anchor: profiles require them, the matrix makes them applicable to UI capabilities, acceptance tests reference the Smart UI standard IDs. `runtime/ui_select.py` runs the package's own selector on an explicit screen context and loads only the standards whose governing control is in the route (`runtime/ui-bindings.yaml`), hash-pinned by `manifest.json`, confined to the package directory and budgeted; everything else is deferred and named. The package itself is untouched.

## 5. Performance and token efficiency

`runtime/contracts.py` caches the known-control set by catalog content; registry build time fell from about 1.2 s to about 0.2 s. Route sizes grew only where profiles now add applicable controls; measurements (UTF-8 bytes measured, tokens estimated) are recorded in the Phase 1 report outside the source tree. The repository never loads the whole Smart UI package: a high-assurance screen with signals in every layer loads about 215 KB (about 4 percent) of the 5.1 MB package, a production screen about 81 KB, and a baseline route nothing.

## Preserved

All 84 v1.0 control identifiers and requirement texts, the frozen v1.0 schemas (byte-identical), the Apache-2.0 licence and founder attribution, and the `release/v1.3.1` branch. Nothing was pushed, tagged or published.
