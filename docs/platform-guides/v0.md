# Using VCGF with v0

**Adapter:** `v0` · **Adapter version:** 1.0.0 · **Framework:** VCGF 1.0.0 · **Status:** stable  
**Platform surface:** v0 web agent and Projects  
**Official verification source:** https://v0.app/docs/instructions  
**Last verified:** 2026-10-02

[← Choose another platform](README.md) · [Adapter reference](../../platforms/v0/README.md) · [Daily VCGF user guide](../user-guide.md)

## Who this guide is for

v0 users working with reusable Instructions, Plan Mode, Projects, and optional GitHub review. You do not need to understand YAML, CI/CD, or the full VCGF control catalog to follow the setup path below. Technical teams can use the same adapter with the deeper control, evidence, and conformance material.

## What you need

- A copy of the VCGF repository or release ZIP.
- Access to your v0 project.
- A chosen VCGF profile: Baseline, Production, or High-Assurance.
- Enough project information to complete the project-context template.

## What VCGF does on this platform

VCGF does not replace v0. It adds a governance layer around how you ask the AI to change software. The adapter gives v0 the persistent or reusable instructions that are appropriate for the verified platform surface, while the VCGF Core remains the source of security and engineering requirements.

The expected behavior is: inspect the existing project, identify impact and risk, apply relevant controls, request human approval when required, make the minimum safe change, test it, and leave evidence.

## Files used by this adapter

### Platform-specific rule files

- `platforms/v0/rules/custom-instructions.md`

### Platform-specific prompts

- `platforms/v0/prompts/pre-change-impact-review.md`

### Supporting VCGF files

- `templates/project-context/project-context.md` — complete the project purpose, architecture, data model, integrations, roles, constraints, and business invariants.
- `templates/project-context/project-security-profile.md` — record security posture and sensitive surfaces.
- One profile under `profiles/` — Baseline, Production, or High-Assurance.
- `checklists/pre-development/pre-development.md` — before meaningful changes.
- `checklists/security-review/security-review.md` — for security-sensitive changes.
- `checklists/pre-release/pre-release.md` — before release.

The supporting files do not have to be copied into a special vendor folder. If your project has a repository or file tree, a practical convention is to keep completed project governance documents under a version-controlled folder such as `docs/vcgf/`. If the platform does not provide a suitable persistent file mechanism, keep the completed documents locally and paste or upload the relevant one when the task requires it.

## Step 1 — Download VCGF

Download the release ZIP from the VCGF GitHub repository, or clone the repository if you use Git.

## Step 2 — Extract the package

After extraction, open `platforms/v0/`. Do not copy the whole VCGF repository into your application unless you intentionally want the full framework as project documentation.

## Step 3 — Choose your VCGF profile

- **Baseline** — prototype, experiment, internal proof of concept, or low-risk app.
- **Production** — real users, business data, internet-facing services, or an application expected to go live.
- **High-Assurance** — sensitive, institutional, regulated, safety/financially significant, or high-impact systems.

If you are unsure and the application will hold real user or business data, start with **Production**.

## Step 4 — Prepare project context

Copy `templates/project-context/project-context.md`, complete it with real project information, and keep it current. At minimum describe:

- what the product does;
- important modules and architecture;
- database or data model;
- user roles and permissions;
- sensitive/personal data;
- integrations and APIs;
- business rules that must not be broken;
- prohibited or approval-required changes;
- build, test, and release commands when relevant.

Do not put passwords, API keys, tokens, or production secrets into the project context.

## Step 5 — Add the platform-specific rules

1. Open the prompt bar, select **+ → Instructions → New Instruction**, and create a VCGF instruction using `platforms/v0/rules/custom-instructions.md`.
2. Apply the VCGF instruction to the conversation before governed work. v0 documentation says selected Instructions remain applied until unchecked.
3. For changes that need review before coding, enable **Plan Mode**; v0 documents that Plan Mode produces a plan and asks for approval before implementation.
4. If the project is GitHub-connected, use the working-branch / pull-request / CI workflow for review evidence. Keep secrets in project environment variables rather than prompts.

## Step 6 — Add supporting VCGF files

You normally do **not** need to load all 84 controls into the AI context. Start with the adapter rule, completed project context, selected profile, and the checklist/template relevant to the current task. The AI can refer to the canonical control catalog or individual controls when deeper detail is required.


## If the platform cannot upload supporting files

VCGF does not require every supporting document to live inside the AI platform. Keep the completed project context, profile record, checklists, and evidence in your normal project documentation or repository. Paste or upload only the document needed for the current task. The persistent adapter rule should tell the AI not to invent missing context; if a required document is unavailable, the AI should label the information unverified and ask for or inspect the missing project source before a sensitive change.

## Step 7 — Start or reopen the AI project

After changing persistent rules or project context, start a fresh session/conversation when practical so you can verify that the intended instructions are active from the beginning.

## Step 8 — Initialize VCGF

### First message to send to the AI

```text
Use the active VCGF Instruction for this task. Before implementing, confirm VCGF 1.0.0, the selected profile, the v0 adapter, affected areas, relevant controls, and whether approval is required. Produce the plan first; do not change code yet.
```

A healthy response should identify the framework/profile/adapter, summarize what it needs to inspect, identify likely risk areas, and **not** jump directly into a sensitive implementation.

## Step 9 — Verify VCGF is active

Use this simple verification question:

```text
What VCGF version, profile, adapter, project-context sources, and governance rules are currently active? Which changes require human approval?
```

Then try a stronger behavioral test:

```text
Add admin access to the application.
```

The AI should not blindly edit code. It should first inspect the existing authorization model, identify affected routes/data/API/database layers, assess access-control risk, explain its plan, and request approval if the proposed change crosses a VCGF approval gate.

**Platform-specific verification:** Confirm the VCGF custom Instruction is checked, optionally enable Plan Mode, then ask v0 to identify the VCGF version/profile and produce an impact plan without code changes.

## Step 10 — Make your first request

A good first request names the desired outcome without telling the AI to skip governance. For example:

```text
Add a profile-photo upload for authenticated users. Follow VCGF. Inspect the current storage and authorization design first, show me the impact and security plan, then wait for approval if required.
```

## Example — Add a feature

**Request:** “Add profile-photo upload.”

**VCGF behavior:** inspect existing storage, allowed file types/size, private/public access, authorization, filename handling, malware/content risk where applicable, error handling, tests, and release evidence.

**Expected outcome:** a feature that fits the current architecture and has explicit upload/download security instead of a UI-only implementation.

## Example — Fix a bug

**Request:** “A user can sometimes see another user’s record.”

**VCGF behavior:** treat this as an authorization/data-isolation issue, reproduce it, inspect server/database enforcement, test allowed and denied cases, apply the minimum safe fix, and retain regression evidence.

## Example — Database change

**Request:** “Add a national ID field.”

**VCGF behavior:** classify the data, determine whether it is necessary, validate format at trusted layers, assess field-level encryption and search/index design, define retention/access rules, create a safe migration, and test existing records.

## Example — Security-sensitive change

**Request:** “Replace the current login flow.”

**VCGF behavior:** classify the change as HIGH or CRITICAL as appropriate, inspect current authentication/session/recovery flows, identify migration and rollback risk, prepare a plan, and stop for approval before changing the security boundary.


## How to request a security review

Use a direct request such as:

```text
Run a VCGF security review for this change. Identify the affected controls, verify trusted-layer authorization and validation, test allowed and denied paths, check secrets/data exposure, list remaining findings, and return security-test evidence. Do not treat a platform scan alone as proof of conformance.
```

Use `checklists/security-review/security-review.md` and `templates/testing/security-test-evidence.md` for a repeatable review record.

## How approvals work

Approval is a deliberate stop before sensitive implementation. The AI should explain what it wants to change, why, the risk, the affected components, the relevant VCGF controls, and the rollback/testing plan. Approve only the described scope. If the plan is too broad, reject it and ask for a smaller safe change.


## What to do when approval is requested

1. Read the exact scope the AI wants to change.
2. Check the stated risk, affected components, controls, tests, migration/rollback steps, and any data/permission impact.
3. Approve only that scope, or reject it and request a smaller plan.
4. If the AI proposes weakening a security control, do not approve it as a shortcut; require a secure alternative or a formal VCGF exception with compensating controls.

A scoped approval can be as simple as:

```text
Approved for the described plan only. Do not expand scope. Run the planned positive and negative tests, preserve existing behavior outside the listed components, and return evidence plus any remaining findings.
```

## How to know the task is complete

A task is complete when the requested behavior works **and** the relevant VCGF completion evidence exists. Depending on the task, that means build/type/lint checks, user-flow verification, positive and negative tests, authorization/data-isolation checks, database migration/integrity checks, security review, regression tests, and a clear statement of remaining findings or approved exceptions. A preview that “looks right” is not enough for a sensitive change.

## How to use checklists

Use the checklist that matches the stage:

- `checklists/pre-development/pre-development.md` before meaningful implementation.
- `checklists/database-change/database-change.md` for schema/migration work.
- `checklists/security-review/security-review.md` for authentication, authorization, data, API, secrets, files, or other sensitive changes.
- `checklists/pre-release/pre-release.md` before release.
- `checklists/production-release/production-release.md` at production release time.

## How to collect evidence

Evidence means proof that a requirement was actually checked. Depending on the task, it may be a passing automated test, browser verification, CI result, security scan, configuration review, threat model, migration test, screenshot where justified, code review, or release checksum.

Use `templates/testing/security-test-evidence.md` and `templates/release/release-evidence.md` when you need a repeatable record.

## How to use templates

Do not fill every template for every task. Use the one that matches the risk:

- `templates/architecture/change-impact-analysis.md` — important changes.
- `templates/security/threat-model.md` — new trust boundaries or high-risk features.
- `templates/security/role-permission-matrix.md` — authorization/RBAC/ABAC.
- `templates/security/field-validation-matrix.md` — important user/API inputs.
- `templates/security/data-classification.md` — personal/sensitive/business data.
- `templates/security/encryption-register.md` — encrypted data and key decisions.
- `templates/database/migration-review.md` — database changes.
- `templates/security/security-exception.md` — when a required control cannot be met and an approved exception is necessary.

## How to use profiles

The selected profile determines which controls are required. Keep the profile ID/version with your project governance records. Moving from Baseline to Production is not just a label change: additional controls and evidence become required.

## When to use Baseline

Use it for prototypes and low-risk work where the application is not yet carrying production obligations. It still requires core protections such as inspection, authentication/authorization basics, validation, injection defense, secrets protection, safe database queries, and regression testing.

## When to use Production

Use it for applications serving real users, employees, customers, business data, or internet-facing services. Production requires most VCGF controls, plus stronger evidence, monitoring, release governance, threat modeling, dependency provenance, and operational protections.

## When to use High-Assurance

Use it for sensitive institutional systems, regulated contexts, high-impact data/permissions, or environments where you need all VCGF v1.0.0 controls and stronger review/evidence expectations.

## How to update VCGF later

1. Read the VCGF `CHANGELOG.md` and the adapter `CHANGELOG.md`.
2. Check framework compatibility in `platforms/v0/adapter.yaml`.
3. Compare the updated rule file with the copy in your project.
4. Review changes to controls/profiles before replacing project governance files.
5. Run the repository validators if you maintain VCGF files in Git.
6. Re-run the activation test after updating persistent instructions.

## Troubleshooting

**The AI starts coding immediately.**  
Re-check that the platform rule/instruction is actually active. Send the initialization prompt again and require an impact plan before code changes.

**The AI cannot identify the profile.**  
Provide the chosen profile explicitly and keep the profile ID/version in project context.

**The AI says a security control is impossible.**  
Do not silently drop it. Ask for the platform limitation, an external control, or a documented exception with compensating controls.

**Instructions become inconsistent in a long session.**  
Start a fresh session, reload persistent instructions/context, and repeat the activation test.

**A platform UI has changed.**  
Use the adapter's `verification/sources.yaml`, `LIMITATIONS.md`, and current official documentation. Do not guess new menu names.

## Platform limitations

VCGF does not assume a project-wide custom-instruction mechanism beyond what current v0 documentation verifies. Re-apply the saved Instruction where needed and keep hard enforcement in code, CI, Vercel/runtime configuration, and repository protections.

Read [`../../platforms/v0/LIMITATIONS.md`](../../platforms/v0/LIMITATIONS.md) for the adapter's canonical limitation record.
