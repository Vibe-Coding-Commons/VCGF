# VCGF Smart UI — Component Lifecycle & Adoption

## حالات دورة الحياة

| الحالة | المعنى | هل يسمح بالتطبيق؟ |
|---|---|---|
| `draft` | فكرة أو معيار غير مكتمل | لا، إلا تجربة معزولة |
| `integration-candidate` | موثق ومختبر على مستوى الحزمة لكن اختبارات التطبيقات ما زالت `not_run` | نعم في مشروع تجريبي أو تبنٍ محكوم |
| `adopted` | تم التحقق من العقد على تطبيقات مستهدفة بأدلة | نعم |
| `deprecated` | ما زال مدعومًا مؤقتًا لكن يوجد مسار بديل | نعم ضمن نافذة الترحيل |
| `retired` | لا يستخدم في تطبيق جديد | فقط دعم إرثي موثق |

## بوابات الانتقال

### Draft → Integration Candidate
يتطلب اكتمال المواصفة، الإعدادات، R01–R12، AC01–AC12، قواعد الاختيار، الروابط، schema، وفحص الحزمة.

### Integration Candidate → Adopted
يتطلب Evidence من تطبيق فعلي وليس من الوثائق وحدها. يجب توثيق التقنية والإصدار والبيانات المصطنعة ونتيجة الاختبارات.

### Adopted → Deprecated
يتطلب ADR يشرح سبب الاستبدال، أثر الترحيل، والمكوّن المقترح بدلًا منه.

### Deprecated → Retired
يتطلب انتهاء نافذة الترحيل وعدم وجود تطبيقات مدعومة تعتمد عليه دون استثناء رسمي.

## إدارة الإصدار

إصدار الحزمة لا يساوي إصدار كل مكوّن. في الحزمة 0.4.0 بقيت المكونات 001–024 عند `0.2.0` والمكونات 025–036 عند `0.3.0` لأن 0.4.0 أضاف طبقة Interaction Patterns ولم يكسر عقود هذه المكونات. أي تعديل يكسر عقد مكوّن يرفع إصداره مستقلًا ويُسجل في CHANGELOG.

## التوافق الخلفي

يعتبر التغيير كاسرًا إذا:
- غيّر معنى قيمة محفوظة.
- حذف حدثًا أو مدخلًا تعاقديًا بلا بديل.
- غيّر ترتيب أولوية إعدادات بما قد يوسع الصلاحية.
- حوّل علاقة مراجعة إلى تفعيل تلقائي.
- غيّر معرف مكوّن أو متطلب منشور.

## التطبيق التدريجي

استخدم شاشة أو وحدة محدودة كـ pilot، ثم:
1. قياس الوضع الحالي.
2. تطبيق المكوّن أو إعادة استخدام الموجود.
3. تشغيل اختبارات القبول والانحدار.
4. مراجعة الشكاوى والأداء.
5. التوسع التدريجي مع إمكانية الرجوع.
