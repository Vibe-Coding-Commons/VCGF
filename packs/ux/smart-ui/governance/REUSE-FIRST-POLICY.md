# Reuse-First Policy — سياسة إعادة الاستخدام قبل الإنشاء

## المبدأ

قبل إنشاء أي مكوّن واجهة أو تثبيت مكتبة جديدة، يجب البحث عن تنفيذ قائم داخل المشروع أو نظام التصميم أو الحزمة التقنية المستخدمة. الهدف هو تقليل التكرار والتبعيات وتكلفة الصيانة، مع عدم التضحية بعقد VCGF أو الأمان والوصولية.

## بوابة الملاءمة

يُعتبر المكوّن الموجود مرشحًا لإعادة الاستخدام عندما تتوفر أدلة على:

1. توافق الوظيفة الأساسية مع المعيار المنطبق.
2. سلامة Component API وعدم ربط الشاشات مباشرة بتفاصيل مكتبة لا يمكن استبدالها.
3. توافق الوصولية ولوحة المفاتيح والاتجاه RTL/LTR في السيناريو المطلوب.
4. عدم وجود تعارض مع الصلاحيات أو عزل المستأجرين أو حدود البيانات.
5. توافق النسخة مع تقنية المشروع الحالية.
6. عدم وجود عيب معروف يجعل تمديده أخطر من استبداله.
7. وجود دليل حديث نسبيًا من كود أو اختبار أو Story/Example أو شاشة عاملة، لا مجرد اسم ملف.

## سلم القرار

`reuse > extend > wrap > replace > build_new`

يُسمح بالقفز إلى `replace` أو `build_new` عندما يوجد سبب موثق مثل تعارض أمني، غياب صيانة، عدم إمكانية تحقيق الوصولية، أو اعتماد تقني منتهي لا يمكن تمديده بأمان.

## منع إعادة الاستخدام الوهمي

وجود مكوّن باسم مشابه لا يثبت التطابق. يجب التحقق من السلوك المطلوب. على سبيل المثال:

- وجود Select يدعم الكتابة لا يثبت شرط البحث داخل أعلى القائمة.
- وجود Hijri Calendar لا يثبت `islamic-umalqura` أو الضبط المحلي.
- وجود File Upload لا يثبت الفحص الخادمي أو الاستئناف.
- وجود زر مخفي حسب الدور لا يثبت التفويض في الخادم.

## سجل الدليل

يسجل لكل قرار:

- `component_or_capability`
- `candidate_path_or_package`
- `evidence_ref`
- `verified_version`
- `fitness`: `fit | partial | unfit | unknown`
- `decision`
- `gap_summary`

الدليل القديم أو غير القابل لإعادة الإنتاج يفرض `verify_first` بدل `reuse`.
