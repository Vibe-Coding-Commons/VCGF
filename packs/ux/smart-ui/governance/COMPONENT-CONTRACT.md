# VCGF Smart UI — Component Contract

**إصدار سجل العقد:** 0.4.0  
**الإطار المستهدف:** VCGF 1.3.0

## الهدف

يعرّف هذا المستند العقد الإلزامي لأي مكوّن يدخل كتالوج **VCGF Smart UI Components & Interaction Standards**. الغرض ليس تحويل الكتالوج إلى مكتبة برمجية يجب تثبيتها بالكامل، بل جعل الذكاء الاصطناعي قادرًا على فهم وظيفة الشاشة، واختيار أقل مجموعة لازمة من المعايير، وإعادة استخدام الموجود قبل بناء شيء جديد.

## القاعدة الأساسية

وجود المكوّن في `catalog.json` يعني أنه **قد يكون مناسبًا**، ولا يعني تفعيله. لا يدخل المكوّن خطة التنفيذ إلا إذا تطابقت إشارة أو أكثر من سياق الشاشة مع قواعد الاختيار، أو صدر قرار معماري موثق يضيفه.

الترتيب القياسي لاتخاذ قرار التنفيذ:

`reuse → extend → wrap → replace → build_new`

وعند غياب الدليل:

`verify_first`

لا يسمح بتحويل `verify_first` إلى `build_new` لمجرد أن فحص الموجود يحتاج جهدًا.

## حقول العقد

كل سجل في `catalog/component-contracts.json` يجب أن يتضمن:

- `standard_id`: معرف ثابت لا يعاد استخدامه لمكوّن آخر.
- `component_name`: الاسم التقني المعتمد.
- `category`: المجال الوظيفي للمكوّن.
- `lifecycle_state`: Draft أو Integration Candidate أو Adopted أو Deprecated أو Retired.
- `criticality`: P0/P1/P2 عند انطباق المكوّن، وليس أمر تفعيل.
- `activation_policy`: دائمًا `explicit-selected-only` في هذه المرحلة.
- `discovery_signals`: الإشارات التي تسمح لمحرك الاختيار بترشيحه.
- `reuse_preference`: ترتيب خيارات التنفيذ.
- `review_relationships`: مكوّنات ينبغي مراجعة تكاملها، من دون تفعيل تلقائي.
- `external_bindings`: معايير خارجية إلزامية عند انطباق نوع الحقل أو التفاعل.
- `required_evidence`: الأدلة اللازمة لرفع حالة التنفيذ.
- `package_policy`: قاعدة اختيار أقل تبعية مناسبة.
- `runtime_test_state`: يبقى `not_run` داخل حزمة المواصفات.

## حدود المسؤولية

عقد المكوّن لا يثبت وجود API أو قاعدة بيانات أو queue أو websocket أو موفر هوية. يجب على Adapter المشروع ربط العقد بالبنية الفعلية. إذا لم توجد القدرة، يسجل Gap؛ لا يخترع الذكاء الاصطناعي endpoint أو خدمة ويصفها بأنها موجودة.

## العلاقات ليست Dependencies تنفيذية

حقل `dependencies` التاريخي في `catalog.json` يُفسر في v0.4.0 على أنه **Review Relationship**. لا يسمح لمحرك الاختيار بتحميل مكوّن لأنه مذكور كعلاقة فقط. مثال: اختيار SmartDataGrid لا يفعّل AdvancedFilterBuilder إلا إذا احتاجت الشاشة فلترة متقدمة فعليًا.

## معايير الاعتماد

لا ينتقل المكوّن من `integration-candidate` إلى `adopted` إلا بعد:

1. ثبات العقد ومعرفاته.
2. نجاح مخططات JSON المحلية.
3. وجود قرار انطباق وإعادة استخدام في مشروع فعلي واحد على الأقل.
4. تنفيذ AC01–AC12 أو مجموعة قبول معتمدة في التطبيق المستهدف بأدلة.
5. فحص يدوي للوصولية، RTL/LTR، والجوال.
6. اختبار التوافق الخلفي أو خطة ترحيل.
7. عدم وجود ملاحظة جودة مفتوحة من نوع blocker.

## الإلغاء والاستبدال

لا يحذف معرف مكوّن منشور. عند الاستبدال:

- يغير `lifecycle_state` إلى `deprecated`.
- يضاف `replacement_standard_id` في سجل تغيير لاحق إذا توسع المخطط.
- تستمر الروابط القديمة في العمل خلال نافذة الترحيل.
- لا يُرقّى المشروع تلقائيًا إلى البديل دون تقييم سياقه.

## مبدأ الحد الأدنى الذكي

أفضل خطة ليست التي تستخدم أكبر عدد من مكونات VCGF، بل التي تحقق المهمة بأقل تعقيد معقول وتحافظ على الأمان والوصولية والاتساق.

## العلاقة مع Smart Interaction Patterns

عقد المكوّن لا يحدد تدفق الحفظ أو التعارض أو الجلسة تلقائيًا. هذه السلوكيات تختارها طبقة [Smart Interaction Pattern Selection](SMART-INTERACTION-PATTERN-SELECTION.md) من `interaction_signals` مستقلة.
