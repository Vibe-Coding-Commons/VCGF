# VCGF-UI-INT-014 - تقدم العمليات طويلة التنفيذ

**LongRunningOperationProgress**

هذه الوثيقة جزء من طبقة **VCGF Smart UI Components & Interaction Standards**، وتحديدًا مكتبة **Smart Interaction Patterns**. وجود النمط في الكتالوج لا يعني تطبيقه في كل شاشة، ولا يعني أن اختيار مكوّن مرتبط يفعّل النمط تلقائيًا. يختار محرك التقييم النمط فقط عندما توجد إشارة تفاعل صريحة أو قاعدة مجال تثبت الحاجة.

النمط يحدد **سلوك الحالة والانتقال والفشل والتعافي وحدود السلطة**، بينما يحدد المكوّن كيف تُمثل عناصر الواجهة. يمكن تطبيق النمط نفسه على React أو Vue أو Laravel أو تطبيق جوال أو تقنية أخرى ما دام عقد السلوك محفوظًا.

لا تعد هذه الوثيقة شهادة امتثال لتطبيق بعينه. حالة اختبارات التطبيق `not_run` حتى ينفذ النمط في مشروع مستهدف وتجمع أدلة قابلة للمراجعة.

## 1. الهدف ونطاق التطبيق

إدارة العمليات التي تتجاوز دورة طلب تفاعلي قصيرة، مع حالة قابلة للاستئناف ومعلومات تقدم ونتيجة نهائية.

**متى ينطبق:** التصدير الكبير والاستيراد والمعالجة الجماعية والتقارير أو الوظائف التي قد تستغرق ثواني طويلة أو دقائق.

**متى لا ينطبق:** لا يحول كل API request إلى Job إذا كان زمنه تفاعليًا ومحدودًا.

**إشارات الاكتشاف:** `long_running_job`, `background_job`, `large_export_job`, `processing_queue`.

قاعدة الاختيار: لا تستنتج النمط من اسم الشاشة فقط. افحص العملية الفعلية، ومصدر البيانات، ودرجة الخطورة، وقابلية التراجع، وحالة الاتصال، واحتمال التزامن. إذا لم توجد إشارة صريحة فالحالة `not_selected` أو `unknown` وليست تفعيلًا احترازيًا.

## 2. عقد الحالة والانتقالات

مخطط الحالة المرجعي:

```text
queued -> running -> succeeded / failed / cancelled / expired
```

هذا المخطط يشرح النية ولا يفرض أسماء متغيرات أو API. يجب أن يعرف التنفيذ لكل انتقال: الحدث الذي بدأه، والجهة التي تملكه، وشرط الدخول، وشرط النجاح، وطريق الفشل، وطريقة الإلغاء أو التراجع إن وجدت.

لا يجوز دمج حالات متباينة في boolean واحد من نوع `loading=true/false` عندما يحتاج السيناريو إلى تمييز `saving`, `retrying`, `conflict`, `forbidden`, `stale`, أو حالة أخرى. كذلك لا تعرض حالة نهائية بناء على توقع الواجهة إذا كان المصدر الموثوق لم يؤكدها.

## 3. الإعدادات والسياسات

القيم التالية **نموذج حوكمة** وليست إعدادًا جاهزًا لكل مشروع. أولوية السياسة: **سياسة النظام → المنشأة → الدور أو المستخدم المسموح → الحالة المؤقتة**. المستوى الأدنى لا يستطيع تخفيف قيد أمني أو توسيع نطاق بيانات.

| المفتاح | النوع | الافتراضي | المعنى والقيود |
|---|---|---|---|
| `progressTransport` | `string` | `"poll-or-event"` | يختار وفق البنية؛ لا يفترض WebSocket. |
| `cancelPolicy` | `string` | `"capability-driven"` | يعرض الإلغاء فقط إذا كان backend يدعم إيقافًا آمنًا. |
| `revalidateAuthority` | `boolean` | `true` | قبل أي أثر مستمر أو انتقال حساس تعاد مراجعة السلطة والصلاحية من المصدر الموثوق. |
| `preserveContextOnFailure` | `boolean` | `true` | يحافظ على سياق المستخدم ومدخلاته المسموح بها عند الخطأ، دون تخزين أسرار. |
| `auditLevel` | `string` | `"risk-based"` | none أو minimal أو risk-based أو full حسب نوع الإجراء وسياسة التدقيق. |
| `telemetryMode` | `string` | `"privacy-aware"` | تقاس الحالات والأزمنة دون إرسال محتوى حساس أو معرفات غير لازمة. |

يجب إصدار مخطط الإعدادات وربطه بالمشروع والمنشأة. التفضيلات المرئية يمكن أن تكون محلية، لكن القرارات التي تحدد الصلاحية أو قابلية التراجع أو نطاق الأثر تبقى في المصدر الموثوق.

## 4. مصدر السلطة وحدود المسؤولية

- الواجهة تملك العرض، التركيز، الرسائل، والتنسيق المؤقت للحالة.
- الخادم أو خدمة المجال يملكان التفويض النهائي، النسخة الحالية، قواعد الأعمال، والآثار المستمرة.
- خدمات الهوية تملك صلاحية الجلسة ومستوى المصادقة، ولا يعاد تفسيرها بمتغير UI.
- عند العمل دون اتصال أو باستخدام cache، يجب تمييز البيانات المؤكدة من البيانات المحلية أو القديمة.
- لا تستخدم ساعة جهاز المستخدم أو وجود زر أو نجاح schema كدليل على نجاح معاملة.
- أي Side Effect يجب أن يمتلك معرفًا أو مرجعًا يسمح بالتتبع والتصالح عندما تصبح نتيجة الطلب مجهولة.

## 5. سلوك المستخدم وتجربة القرار

يجب أن توضح الواجهة للمستخدم **ما الحالة الحالية، وما الإجراء المتاح، وما أثره، وما الذي ينتظر الخادم**. لا تستخدم Toast عام كبديل لحالة مستمرة، ولا تمنع الصفحة كلها إذا كان جزء واحد فقط ينتظر.

عند وجود قرار، استخدم أسماء أفعال واضحة بدل نعم أو لا. وعند وجود خطر فقد عمل أو أثر غير قابل للعكس، وفر حاجزًا متناسبًا مع الخطر. ينبغي أن يستطيع المستخدم إلغاء المسار عندما يكون الإلغاء حقيقيًا، وألا يعرض زر Cancel إذا كان يغلق النافذة فقط بينما يستمر الأثر في الخلفية دون توضيح.

## 6. الفشل والتعافي والاستجابات المتأخرة

كل نمط يجب أن يميز بين الأخطاء القابلة لإعادة المحاولة والأخطاء التي تحتاج تصحيح مدخلات والأخطاء التي تعني فقد صلاحية أو تعارض نسخة. لا يُسمح بإعادة المحاولة التلقائية لأمر قد يكرر أثرًا ما لم توجد حماية idempotency أو عقد مكافئ.

عند تغير الشاشة أو السجل أو المرشح أو الجهة أو الحساب، تُلغى الطلبات السابقة أو تُعلّم قديمة ويُمنع ردها من تعديل الحالة الجديدة. إذا فُقد الاتصال بعد إرسال أمر كتابة وقبل استلام النتيجة، لا تفترض النجاح ولا الفشل؛ طبّق reconciliation أو استعلام حالة إن كان المجال يسمح.

## 7. الأمن والخصوصية والتفويض

- يعاد التحقق من التفويض في المصدر الموثوق لحظة تنفيذ الأثر.
- إخفاء زر أو تعطيله لا يمثل قرار Authorization.
- لا تُخزن كلمات المرور أو OTP أو الرموز أو حقولًا محظورة ضمن مسودات أو Snapshot أو Telemetry.
- تبديل المستأجر أو الدور أو الحساب يعيد تقييم السياق والـcache والطلبات المعلقة.
- الرسائل لا تكشف وجود كيانات أو حقول غير مسموح للمستخدم بمعرفتها.
- سجلات التدقيق والقياس تجمع الحد الأدنى اللازم، مع فصل التشخيص عن محتوى الأعمال الحساس.

## 8. إمكانية الوصول وإدارة التركيز

كل حالة مرئية يجب أن تكون قابلة للإدراك دون اللون وحده. استخدم `aria-live` أو دلالات الانشغال والخطأ عندما تكون مناسبة، ولا تكرر الإعلانات عند polling أو progress سريع. عند فتح حوار قرار يُنقل التركيز إلى بداية منطقية ويعود بعد الإغلاق إلى مصدر صالح.

إذا اختفى عنصر بسبب تغير صلاحية أو تحديث بيانات فلا تعِد التركيز إليه. عند Retry أو Conflict أو Session Expiry يجب أن يعرف مستخدم لوحة المفاتيح أين انتقلت المهمة، وأن تبقى الرسائل مرتبطة بالعناصر ذات الصلة.

## 9. التعريب والاستجابة والأجهزة

يدعم النمط العربية والإنجليزية وRTL/LTR والنص المختلط. لا تفترض أن ترتيب الأزرار الخطر والآمن ثابت باتجاه بصري واحد؛ اعتمد المنطق الدلالي ونظام التصميم. على الجوال يجب ألا تغطي الرسائل أو أشرطة التقدم الإجراء الأساسي، وعلى الشاشات الكبيرة لا تُبعد حالة العملية عن موضعها حتى يفقد المستخدم العلاقة.

تُترجم نصوص الحالات والأخطاء والأفعال، بينما تبقى معرفات الحالة والأوامر داخل العقود البرمجية مستقلة عن اللغة.

## 10. الأداء والمرونة

يجب تعريف Budget مناسب للمهمة: زمن ظهور Feedback، زمن اعتبار العملية طويلة، وتكرار Polling أو Retry إن وجد. لا تستخدم timers ثابتة بوصفها حقيقة أعمال. عمليات الخلفية الطويلة تحتاج آلية استئناف بدلاً من إبقاء اتصال HTTP أو Spinner لا نهائي.

يجب اختبار السلوك تحت تأخير الشبكة، الطلبات المتقاطعة، تغير البيانات، العودة من الخلفية، وإعادة الاتصال. القياس يثبت التحسن؛ لا تكفي عبارة سريع أو Responsive.

## 11. المراقبة والتدقيق والأدلة

سجل أحداث الحالة المهمة بأسماء مستقرة مثل `intent_started`, `request_sent`, `server_confirmed`, `rolled_back`, `conflict_detected`, `permission_revoked` حسب النمط. لا تسجل payload كاملًا بلا حاجة.

كل Acceptance يحتاج دليلًا يناسبه: اختبار وحدات لحالة منطقية، اختبار تكامل لعقد الخادم، E2E للتفاعل، فحص يدوي للوصولية، أو قياس أداء. حالة `not_run` تبقى كما هي حتى يوجد تنفيذ فعلي.

## 13. حالات القبول القابلة للتتبع

<a id="VCGF-UI-INT-014-AC01"></a>
### VCGF-UI-INT-014-AC01 - قبول هوية Job مستقرة

**Given:** وجود شاشة ينطبق عليها نمط «تقدم العمليات طويلة التنفيذ» مع حالة ابتدائية معلومة ومصدر سلطة موثق

**When:** يحدث السيناريو المرتبط بمتطلب «هوية Job مستقرة» وتنتقل الحالة عبر مسار النمط

**Then:** تتحقق القاعدة التالية دون فقد سياق أو تجاوز صلاحية: يمتلك المستخدم مرجعًا يمكن الرجوع إليه دون إعادة بدء العملية.

**Evidence:** لقطة أو سجل اختبار آلي أو يدوي يثبت الحالة قبل وبعد، والطلب أو الاستجابة ذات الصلة عند الحاجة، وحالة التركيز أو الإعلان الوصولي عندما يكون التفاعل مرئيًا.

**الحالة في هذه الحزمة:** `not_run` حتى تطبيق النمط في مشروع فعلي.

### VCGF-UI-INT-014-AC02 - قبول تقدم صادق

**Given:** وجود شاشة ينطبق عليها نمط «تقدم العمليات طويلة التنفيذ» مع حالة ابتدائية معلومة ومصدر سلطة موثق
